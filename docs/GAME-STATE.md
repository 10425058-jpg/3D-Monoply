# 3D Monopoly — Game State Contract

**Status:** v1.0.0 implementation baseline (types illustrative until implemented)  
**Purpose:** Shared TypeScript-oriented model for Frontend, Backend, and Socket.IO payloads.

## 1. Important distinction

The existing local frontend store in `src/store/useGameStore.ts` contains both gameplay state and presentation state. Online mode must separate them.

**Server-authoritative state:** players' money/positions, current turn, turn phase, dice result, property ownership, houses, mortgage, auction, trade, debt, cards, winner, and match status.

**Client-only presentation state:** camera mode, game speed, hovered/selected space, modal visibility, graphics quality, sound settings, animation progress, and local UI logs.

Do not send client-only presentation state to the backend as game truth.

## 2. Proposed TypeScript types

These are contract examples, not files already implemented in the app.

```ts
type Id = string;

type RoomStatus = "WAITING" | "IN_PROGRESS" | "CLOSED";
type MatchStatus = "IN_PROGRESS" | "FINISHED" | "ABANDONED";

type TurnPhase =
  | "PRE_ROLL"
  | "ROLLING"
  | "MOVING"
  | "LANDED_ACTION"
  | "CARD_DRAWN"
  | "DEBT_RESOLUTION"
  | "END_TURN"
  | "GAME_OVER";

type PlayerConnectionStatus = "CONNECTED" | "DISCONNECTED";

interface PlayerState {
  playerId: Id;          // unique seat/participant ID within a match
  userId: Id;            // persistent account ID
  username: string;
  avatarUrl: string | null;
  token: string;         // token/skin identifier
  color: string;
  position: number;      // board space ID/index per agreed board definition
  money: number;         // integer
  inJail: boolean;
  jailTurns: number;
  isBankrupt: boolean;
  connectionStatus: PlayerConnectionStatus;
  seatOrder: number;
}

interface PropertyState {
  spaceId: number;       // stable ID from board data
  ownerPlayerId: Id | null;
  houses: number;
  isMortgaged: boolean;
}

interface DiceState {
  values: [number, number];
  total: number;
  rolledByPlayerId: Id;
}

interface MatchState {
  matchId: Id;
  roomId: Id;
  status: MatchStatus;
  mapId: string;
  rulesetId: string;
  players: PlayerState[];
  properties: PropertyState[];
  currentPlayerId: Id;
  turnNumber: number;
  turnPhase: TurnPhase;
  dice: DiceState | null;
  doublesCount: number;
  winnerPlayerId: Id | null;
  stateVersion: number;
  startedAt: string;
  updatedAt: string;
}

interface RoomMember {
  userId: Id;
  username: string;
  avatarUrl: string | null;
  isReady: boolean;
  isHost: boolean;
}

interface RoomState {
  roomId: Id;
  status: RoomStatus;
  mapId: string;
  maxPlayers: number;
  isPrivate: boolean;
  members: RoomMember[];
  matchId: Id | null;
}
```

## 3. Mapping from current frontend model

The current local model uses `Player.id` as a numeric local identifier and `PropertyState.ownerId` as a local player ID. For online mode:

| Current local field | Proposed online field | Notes |
|---|---|---|
| `Player.id` | `playerId` + `userId` | Separate match seat from account identity |
| `Player.name` | `username` | Server-provided display name |
| `Player.position` | `position` | Server authoritative |
| `Player.money` | `money` | Server authoritative integer |
| `Player.isAI` | server player kind / seat metadata | Decide how AI is represented |
| `properties[spaceId].ownerId` | `ownerPlayerId` | Null when unowned |
| `currentPlayerIndex` | `currentPlayerId` | Avoid array index as identity |
| `turnPhase` | `turnPhase` | Agree exact enum values |
| `dice` | `dice` | Server generated in online mode |
| `auction` | `auction` snapshot | Server authoritative |
| `pendingDebt` | `pendingDebt` snapshot | Server authoritative |
| `railroadRaid` | custom event/state | Confirm whether retained in online rules |

The current `src/types/game.ts` should remain the source for local-mode types until an intentional online adapter is implemented. Do not silently change existing local gameplay types as part of backend setup.

## 4. Board and map identifiers

- Use stable board `spaceId` values that match the current board data.
- Use a stable `mapId`, initially proposed as `central-castle`.
- Store a `rulesetId` and optionally a board/content version with each match.
- Frontend and Backend must use compatible board definitions. Locked: backend owns versioned board content `central-castle@1`; clients declare matching content version and cannot submit prices. A shared data package can be introduced later.

## 5. State versioning

Every committed match state change increments `stateVersion` by one (or uses a documented event sequence strategy). Clients ignore stale updates and request a snapshot when a version gap is detected.

## 6. Invariants the server must enforce

- Only the current player can perform current-turn actions.
- Only actions allowed in the current `turnPhase` are accepted.
- Dice values are generated by the server.
- Player money cannot become negative unless the rules explicitly represent debt.
- Property owner must be a player in the same match or null.
- A property cannot be purchased twice.
- Rent, taxes, rewards, and building prices are calculated by server rules.
- A match has at most one winner.
- A repeated `clientActionId` cannot apply the same action twice.

## 7. AI and meta progression

The existing local game includes AI turns and meta progression (daily rewards, missions, wheel, stickers). These features should not be assumed to be in the first multiplayer release.

Locked: online rooms support 2–4 human participants only for first release. Meta progression is deferred; existing local AI remains intact.

## 8. Locked v1 state semantics

- Apply the [API Contract v1.0.0](./API-CONTRACT.md#contract-v100--locked-implementation-decisions-2026-11-10) decision record over any older draft phrasing.
- `mapId` is `central-castle`, `rulesetId` is `classic-v1`, and content version is `central-castle@1`.
- Every gameplay command includes UUID `clientActionId` and integer `expectedStateVersion`; backend increments `stateVersion` once per committed command and emits ordered notifications with the committed version. Multiple notifications for the same commit may share that state version and have different event IDs; consumers must not assume one event per version.
- Preserve client-only camera/UI/animation settings outside `MatchState`.
- `PlayerState.userId` remains required for online human-only MVP. Server AI seats are deferred.
- Only server snapshots are authoritative; client local game types do not automatically become online contracts.
- Reconnected participants receive a full snapshot. A 120-second disconnect grace window precedes a paused match, not automatic forfeiture.
